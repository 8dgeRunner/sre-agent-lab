# Design: 低资源、合规的运维 Agent 混沌靶场

## Problem Statement

建立一个不接触业务生产数据、可在 Contabo 单 VPS 上运行的运维 Agent 训练靶场。首期以 k3s 平台故障和极小微服务故障为核心，PostgreSQL、Redis 按场景临时启动；FoundationDB 作为独立高级专项。靶场支持故障注入、观测、诊断、修复、回滚和评分，并逐步提高 Agent 权限。

## What Makes This Useful

每个练习都是可重放的“故障剧本”：合成流量和合成数据承载业务假设，故障注入器制造 outage，观测信号呈现症状，Agent 只能通过受控工具操作，系统根据恢复时间、数据正确性、动作安全性和证据完整性评分。这样练的是运维闭环，而不是背命令。

## Evidence From Current Practice

- AWS FIS 把 experiment 建模为 actions、targets、stop conditions，并强调先在 pre-production 验证；停止条件由监控告警触发。
- Netflix ChAP 用实验组/对照组和小流量 canary 控制 blast radius，并以 error budget circuit breaker 自动终止实验，接入 CD 持续重复验证。
- Azure Chaos Studio 将 Workspace、Scenario、报告、service-direct/agent-based fault 与影响分析组合起来，并已提供面向 Agent 的插件接口。
- LitmusChaos 和 Chaos Mesh 都以 Kubernetes CRD、工作流、steady-state probe、结果资源和 Prometheus 指标为核心。
- ChaosBlade 曾作为候选方案调研，但当前路线已暂停：不安装、不接入 scenario 枚举，也不作为 Chaos Mesh 的 fallback。
- FoundationDB 用确定性、可重复的 Simulation 覆盖网络、机器、数据中心故障，夜间运行大规模模拟；这是 FDB 场景应优先借鉴的测试方式。
- Microsoft AIOpsLab 将环境部署、故障注入、负载、遥测、Agent 接口和问题评分统一成可扩展 benchmark。
- AgenticOpsEval 的 AIOps2025 与 RCA100 提供 503 个专家标注案例、约 15.3 GB 多模态数据，并按 Localization、Identification、Reason 评估 Agent。AIOps2025 提供 Metrics/Logs/Traces 与关键证据；RCA100 进一步提供 Events/Alerts/Topology、显式因果链和 661 个证据检查点。

真实 ground truth 分布决定首期组件：

- AIOps2025 的 400 例中，Pod failure 45、node memory 38、I/O 28、网络损坏/延迟/丢包 73、CPU/内存压力 42、DNS 21、targetPort 错配 18、Pod kill 15；这些都直接落在 k3s/Kubernetes 层。
- AIOps2025 另有 JVM 55 例和 code error 21 例，需要一个按需 Java fault service，而不是中间件集群。
- RCA100 的 103 例中，memory pressure 12、node CPU 12、5xx 11、限流 11、CPU full load 8、流量激增 6、缩容 6，占主要部分。
- RCA100 中 PostgreSQL 可承载 slow SQL 5 与 DB network latency 2；Redis 可承载 unavailable 4 与 cache breakdown 1；消息队列积压只有 1 例；FDB 为 0 例。

## Constraints

- Contabo 当前只读检查结果：6 vCPU、约 11 GiB RAM、根盘剩余约 56 GiB；k3s 当前未运行。
- 低常驻资源优先：PostgreSQL、Redis、FDB 和观测组件按场景启停，不追求所有组件同时在线。
- 只使用合成数据、独立凭据、隔离 namespace/网络和不可访问生产网段。
- Agent 分级自治：检测 → 诊断 → 提案 → 人工批准执行 → 受限自动恢复。
- 不自研底层故障注入器，采用成熟工具并自建 scenario、policy、评分和审计编排。
- AgenticOpsEval 受非商业许可证约束：AIOps2025 为 CC BY-NC 4.0，RCA100 为 CC BY-NC-SA 4.0；衍生数据与分发必须保留出处并遵守非商业限制。

## Premises

1. 单节点 k3s 足以完成第一阶段训练；真实主机宕机、跨节点网络分区和 FDB 故障域测试延后到临时三节点环境。
2. 靶场的核心资产是可重复的 scenario 和评分数据，而不是长期运行的中间件集群。
3. 所有写操作都经过 allowlist、TTL、stop condition、自动回滚和审计；Agent 不获得宿主机 root 或云账号权限。
4. 公开数据集主要提供历史观测和真值，不等于原环境的可执行故障配方；live 场景只能声明为“行为等价复现”，不能声称精确复现原事故。

## Approaches Considered

### Approach A: 轻量闭环（选择）

单节点 k3s；首个 live MVP 只运行两个极小 HTTP 服务、Prometheus 和日志采集，使用 Kubernetes API 制造配置、调度、生命周期和资源故障。Toxiproxy、PostgreSQL、Redis、Chaos Mesh 和 FDB 都作为按需适配器。自建轻量编排器统一 scenario、工具调用、stop condition、评分和报告。

优点：资源最省，最贴合现有 SRE 技能，数小时可重置；缺点：首期多工具组合需要统一生命周期和权限模型。

### Approach B: 标准基准

以 AIOpsLab 的 problem registry、Agent API 和 orchestrator 为评测骨架，接入 Chaos Mesh、AgenticOpsEval、PostgreSQL/Redis 场景与本地观测栈。

优点：标准化和跨 Agent 对比最好；缺点：组件较重，需裁剪部署，且 AIOpsLab 的现成问题主要偏微服务/Kubernetes，需要自建中间件问题。

### Approach C: 确定性仿真优先

先做 AgenticOpsEval 故障事件回放和离线评分，再把可复现场景映射到 k3s；FDB Simulation 作为独立扩展。

优点：数据安全、回放和回归最强；缺点：早期不能练真实 kubectl、网络、日志和恢复动作，工程投入较大。

## Recommended Approach

采用 A，接口设计兼容 B：scenario schema 固定为 `lab.scenario/v1alpha1`，必填 `problem_id`、`seed`、`workload`、`faults`、`steady_state`、`allowed_tools`、`stop_conditions`、`recovery`、`grading`。Agent 只实现 `observe()`、`propose()`、`act()`、`explain()` 四类能力。未来可把同一 scenario 注册到 AIOpsLab，而不重写 Agent。

在 live 靶场前增加 AgenticOpsEval 数据桥。统一内部格式 `lab.case/v1alpha1`，包含 `task`、`time_window`、`entities`、`topology`、`modalities`、`ground_truth`、`evidence_checkpoints`、`license`。同一 Agent 接口既能查询离线 Parquet/JSON，也能查询 live Prometheus、日志和 Kubernetes API。

数据流：

```text
scenario.yaml -> safety admission -> fault runner -> synthetic workload
       |                 |                  |              |
       +------------ telemetry/事件 -------+--------------+
                              |
                    agent tool gateway
                              |
              evidence + recovery + grader -> report/trace
```

```text
AgenticOpsEval -> dataset adapter -> normalized case -> offline tool gateway
                                            |                 |
                                            +---- RCA grader --+

normalized case -> reproducibility gate -> live candidate | offline-only
```

## Implementation Plan

### 1. 基础环境与安全边界

- 用 k3s 单节点、独立 `chaos-lab` namespace、NetworkPolicy、ResourceQuota 和 Pod Security 限制运行。
- 所有练习由一次性 Job/Helm release 启动，结束后销毁；默认不安装重型 Dashboard。
- 工具网关采用 allowlist：只暴露只读查询、受限 `kubectl`、PostgreSQL/Redis/FDB 状态查询和带 TTL 的恢复动作；禁止任意 shell、宿主机路径、云 API 和生产 kubeconfig。
- 每个实验拥有 TTL、唯一 run_id、预算和 emergency stop；任何 stop condition 触发即先 destroy/recover 再评分。
- privileged 能力默认关闭，Agent 永远不获得。需要 privileged daemon 的 Chaos Mesh 网络/主机模式必须单独审批；默认 live 路径只使用 namespace-scoped PodChaos、Kubernetes API 和合成服务 fault flag。
- 单 VPS 资源硬上限：k3s/系统保留 2.5 GiB，两个极小服务合计 384 MiB，Prometheus/日志采集合计 768 MiB，编排器/Agent 合计 768 MiB，PostgreSQL 或 Redis 场景上限 768 MiB，实验突发余量 1.5 GiB；FDB 专项不得与数据库场景同时运行。实验数据与镜像总占用不超过 25 GiB，低于 20 GiB 可用空间时拒绝启动。

### 2. 观测与合成业务

- 使用 `frontend -> backend` 两个极小 HTTP 服务产生合成请求，支持延迟、5xx、限流、死循环、异常退出和下游调用；请求携带 trace_id。
- Prometheus 抓取节点、k3s、应用、PostgreSQL、Redis 和 FDB 指标；日志统一 JSON；Kubernetes Events 作为一等观测源，不引入 Grafana或长期时序存储。
- steady state 至少包括成功率、P95 延迟、5xx/429、Pod ready/restart、Pending 时长、DNS/连接错误、数据库查询延迟、Redis 命中率和恢复时间。

### 2.5 AgenticOpsEval 数据桥

- 不把完整 15.3 GB 数据集下载到 Contabo。RCA100 按 task 流式读取并设置 2 GiB LRU 缓存；AIOps2025 的日级归档只在开发机或独立对象存储解析，再导出案例时间窗切片。
- 第一批使用 RCA100 的 20 个分层案例和 AIOps2025 的 20 个案例；其余案例作为隐藏评测集，Agent 运行时不能读取 answer key。
- 数据适配器提供 `query_metrics`、`search_logs`、`query_traces`、`list_events`、`get_alerts`、`get_topology` 六类只读工具。所有返回结果带 `evidence_id`，Agent 必须引用证据才能获得 Reason 得分。
- 采用论文原始离线评分：AIOps2025 为 Localization 0.40、Type 0.40、Evidence 0.10、Efficiency 0.10；RCA100 为 Entity 0.40、Fault 0.30、Reasoning Process 0.30。live 处置评分单独报告，禁止混为一个总分。
- 数据固定划分为 development、validation、hidden-test，并按故障类型和根因实体分层，避免相同故障实例或相邻时间窗跨集合泄漏。
- 每次运行记录 dataset version、case ID、文件 checksum 和适配器版本，确保评分可以重复。

### 3. 场景阶梯

- L0 k3s 原生：Pod failure/kill、CrashLoopBackOff、restart flapping、Pending/Unschedulable、replicas=0、resource limit 错配、Service/Endpoints 错配、NetworkPolicy 隔离、DNS 失败。
- L1 资源与网络：Pod CPU/memory pressure、node CPU/memory/disk 告警、网络延迟/丢包/损坏、I/O fault。单节点上的 node 故障只做受控压力或离线回放，不执行 node down/OOM。
- L1 应用：HTTP 5xx、429 限流、流量激增、热点请求、CPU 死循环、线程耗尽、空指针/代码错误；JVM GC/latency/exception 仅在按需 Java fault service 中运行。
- L1 数据依赖：PostgreSQL 覆盖 slow SQL、DB network latency；Redis 覆盖 unavailable、cache breakdown。两者不常驻，每次只启动一个。
- L2 FDB 专项：事务冲突、客户端超时、进程恢复和网络抖动，优先使用官方 Simulation；不将其计入 AgenticOpsEval 对齐率。
- 每个场景必须有 hypothesis、注入动作、预期信号、停止条件、恢复动作、数据不变量和评分函数。
- 数据集案例先分类：Pod 生命周期、调度、Service、NetworkPolicy、DNS、资源压力、网络和端口错误直接进入 live 候选；slow SQL/DB latency 映射到 PostgreSQL，Redis 故障使用按需 Redis；JVM 和错误代码仅在匹配 fault service 中复现；node down/OOM、TiDB 专属 I/O 和缺少注入参数的案例保持 offline-only。
- live 转换采用“症状契约”而不是复制原资源名：要求关键指标方向、日志/Trace 证据、传播路径和根因类型一致，服务名、云资源 ID 与具体阈值映射到本地合成系统。

### 4. Agent 训练与评分

- 阶段 1 只读诊断：给 Agent 结构化工具结果和时间线，评分根因、证据引用、误报和时间。
- 阶段 2 提案：要求给出风险、影响范围、验证命令、回滚计划；人工批准后执行。
- 阶段 3 受限执行：动作必须带目标、TTL、预算和预期结果；网关拒绝越权或无回滚动作。
- 阶段 4 自动恢复：仅允许预批准 playbook；恢复后必须重新跑 steady-state 和数据校验。
- v1 总分 100：根因与证据 35、恢复结果 30、动作安全 20、效率 10、报告完整性 5。数据不变量失败或越权动作实际执行时总分直接为 0；被网关拒绝的越权尝试每次扣 10 分。
- 重放以 `scenario_version + seed + workload_image_digest + fault_adapter_version` 定义；同一组合必须产生相同目标选择和故障时间线。外部时间抖动记录为环境差异，不允许修改标准答案。
- 每次 run 保存结构化轨迹：观测摘要、证据 ID、工具名与参数、结果摘要、告警、动作、回滚和评分；不保存隐藏推理或敏感原始数据。默认保留 30 天，聚合分数保留 180 天，删除前执行字段级脱敏检查。
- 训练结果拆成三块：`offline-rca` 衡量定位、识别和证据链，`live-diagnosis` 衡量实时工具使用，`live-remediation` 衡量恢复、安全和数据不变量。三块都达标后才提升 Agent 自治等级。

### 5. 四周实施节奏

- 第 1 周：实现 `lab.case/v1alpha1`、RCA100 单案例流式读取、六类离线工具和论文 grader；在 20 个案例上建立只读 Agent baseline。
- 第 2 周：部署两个极小 HTTP 服务和基础观测，完成 CrashLoop、Pending、replicas=0、resource limit、Service targetPort、DNS 六个纯 k3s 场景。
- 第 3 周：增加 NetworkPolicy、CPU/memory pressure、5xx、429、traffic surge；把至少 4 个数据集案例转换为行为等价 live 场景。
- 第 4 周：按需加入 PostgreSQL slow SQL/DB latency 与 Redis unavailable；加入提案审批、受限恢复和 20 次回归。FDB 仅设计独立 Simulation 适配器。

## Success Criteria

- 单 VPS 在 10 分钟内完成一次环境启动，在 5 分钟内完成一次实验清理，常驻内存不超过 6 GiB。
- 12 个 k3s/应用基础场景各重复运行 20 次，同一 replay key 的目标选择和故障时间线一致。
- Agent 能在只读模式下对至少 80% 基线场景给出正确根因和证据；受限恢复不得产生越权动作。
- 所有场景只使用合成请求；PostgreSQL/Redis 场景能验证查询结果、缓存行为和恢复后数据不变量；FDB 专项能验证事务不变量。
- 任一 stop condition 都能在 60 秒内停止注入并完成清理；实验报告包含 hypothesis、影响、动作、恢复和评分。
- 离线适配器无需下载完整数据集即可运行单个 RCA100 task；相同 checksum 和版本的评分完全一致。
- Agent 在隐藏离线集上达到 Localization/Entity ≥ 70%、Fault Type ≥ 70%、Reason/Evidence ≥ 60%，每条关键结论均引用有效 `evidence_id`。
- 至少 12 个公开数据集案例完成可复现性评审，其中 8 个转换为 live 场景，其余明确记录 offline-only 原因。

## Distribution Plan

仓库内以 Helm/Kustomize、scenario YAML、Agent tool schema 和 `make lab-up/lab-run/lab-down` 分发；GitHub Actions 只执行静态校验、scenario 单元测试和离线 grader 测试，不在 CI 运行 privileged chaos。真实实验在 Contabo 手动或定时触发。

## Not In Scope

- 首期不做生产环境混沌、不接真实业务数据、不授予云账号或宿主机 root。
- 首期不做多租户 Web 控制台、不做全量 AIOpsLab 部署、不做自研 FDB 内核级故障模拟。
- 首期不追求三节点 HA；需要真实节点故障时再创建短期三节点环境。
- 不训练或评测隐藏思维链；Reason 只根据显式证据引用、因果节点和可验证检查点评分。
- 不把 AgenticOpsEval 原始资源名、拓扑或数值硬编码为 live 答案，也不在 Contabo 解压完整 AIOps2025 数据集。
- 首期不部署 Kafka/RocketMQ；RCA100 仅 1/103 为消息队列积压，不值得引入常驻消息系统。
- 首期不把 k3s 上游软件缺陷混入 AgenticOpsEval 对齐场景；k3s issue/CVE/升级回归作为独立题库管理。

## The Assignment

先实现 RCA100 `t001` 的离线读取闭环，再部署两个极小 HTTP 服务，实现 `targetPort misconfig` live 场景：Agent 必须通过 Service、Endpoints、Pod、Events、日志和指标定位错误，修复后验证 steady state。该模板随后复制到 DNS、NetworkPolicy、CrashLoop 和 Pending 场景。
